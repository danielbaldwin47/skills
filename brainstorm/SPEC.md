# Spec: `/brainstorm`

Synthesised from the grilling session on 2026-08-16. Design doc for the skill; the runbook (`SKILL.md`), lens list (`lenses.md`) and skill map (`README.md`) are built from this.

## Problem Statement

When I have an open problem — a product direction, an architecture choice, a name, a life decision — I want to generate a wide field of options fast and then think about them, in my own words, with something pushing back and riffing. What I get from a bare "give me ideas" prompt is a flat list that either converges too early (the model picks a winner for me) or has no shape (twenty variations on the obvious idea, no wild ones, no coverage of the boring-but-necessary ones). Nothing is kept, so a second session starts from zero, and I never learn which prompting angles actually produce ideas I like.

## Solution

`/brainstorm <topic>` runs a light, phased session: a short vibe check, one wide pass of 10–20 terse, numbered ideas each tagged with the lens that produced it, a stop where I write freely about which ones grab me, and a deepen phase where the skill asks what pulls me to each standout and riffs on it — sub-variants, adjacent ideas, tensions — without deciding for me. The session lands in a light markdown doc (one per topic) that a later session can pick up and build on ("more like #4", "fresh ideas", "the goal has shifted"). Lenses live in an editable sidecar file, and the doc records which lenses produced my standouts, so the lens set is tunable by hand over time.

The skill is a sparring partner, not a decider.

## User Stories

1. As a user, I want to invoke `/brainstorm <topic>` (or say "brainstorm …") and get a session going, so that ideation is one command away.
2. As a user, I want the skill to ask me at most three short vibe-check questions before generating, so that ideas are aimed at what I actually want without a long interview.
3. As a user, I want the vibe-check questions chosen from a fixed menu (real goal / success shape, hard constraints, already tried or ruled out) based on what my invocation left unsaid, so that I'm never asked what I already told it.
4. As a user, I want the vibe check skipped entirely when my invocation already covers goal, constraints and prior attempts, so that a detailed prompt goes straight to ideas.
5. As a user, I want the skill to NOT read repo files, git history, or any local context by default, so that ideas aren't quietly steered by whatever happens to be in cwd.
6. As a user, I want to be able to say "look at the repo" (or name a file) and have the skill read README/CLAUDE.md and the top-level tree — and only that unless I name more — so that code-adjacent brainstorms can be grounded on request.
7. As a user, I want 10–20 numbered ideas per round, each ≤20 words, so that I can scan the whole field in one screen and refer to ideas by number.
8. As a user, I want each idea tagged inline with the lens that produced it (e.g. `[inversion]`), so that I can see coverage while picking and learn which lenses hit.
9. As a user, I want the ideas to be generated by working through a fixed set of lenses with at least one idea per lens, so that the list covers bases (obvious, cheapest) and stretches (inversion, question-the-premise) rather than clustering around one angle.
10. As a user, I want the eight starter lenses to be: obvious, inversion, borrow-from-another-domain, remove-a-constraint, add-a-harsh-constraint, cheapest-possible, most-ambitious, question-the-premise — so that the first version has a balanced spread.
11. As a user, I want two further lenses (combine-two-ideas, what-would-[archetype]-do) held back for follow-up rounds, so that "more" has fresh angles.
12. As a user, I want the lens list to live in a small editable file next to the skill, so that I can add, remove, or reword lenses without touching the runbook.
13. As a user, I want the skill to stop after the list and ask, in one line, which ideas grab me and any thoughts — as free text, not a multiple-choice widget — so that I can respond in my own words.
14. As a user, I want to be able to pick zero and say "more" / "none of these" / "more like #4" / "something wilder", and have the skill run another round steered by that, so that I'm never forced to pick.
15. As a user, I want the deepen phase to ask me, per standout, what pulls me to it, then riff — 3–5 sub-variants or adjacent ideas plus one "what would need to be true" line — so that the deepening is a conversation, not a verdict.
16. As a user, I want the deepen phase to avoid ranking, recommending, or "who else has done this" comparisons unless I ask, so that I stay in generative mode.
17. As a user, I want to be able to say "make #3 concrete" and get effort (S/M/L) and a first step for that idea, so that concreteness is available on demand.
18. As a user, I want the session written to a light markdown doc, so that it survives the session and can be picked up later.
19. As a user, I want the doc at `./brainstorm-<slug>.md` when I'm inside a git repo, and at `~/brainstorms/<slug>.md` otherwise, so that project brainstorms live with the project and everything else lands in one place.
20. As a user, I want the doc structured as: Goal & vibe (my answers, my words) / Ideas (all rounds, tagged) / Standouts (my picks, my thoughts, the riffs) / Threads (loose half-thoughts, tensions, things to revisit) / Lens notes (one line: which lenses produced standouts), so that it's readable at a glance and tunable.
21. As a user, I want the terminal to show a terse recap plus the doc path at the end, so that I know where it went without opening it.
22. As a user, I want to continue a previous brainstorm by referencing it ("more on the running-brand brainstorm", or invoking with a topic whose slug matches an existing doc), without a special keyword, so that follow-up is natural.
23. As a user, I want the skill to confirm in one line before appending to an existing doc, so that a slug collision doesn't silently merge unrelated brainstorms.
24. As a user, I want a continuation to read the doc, avoid duplicating existing ideas, use held-back or named lenses, and append as `### Round N` under Ideas, so that the doc grows rather than resets.
25. As a user, I want to be able to say the goal or brief has changed and have the skill update Goal & vibe and note what changed, so that the doc tracks how my thinking moved.
26. As a user, I want `/brainstorm quick <topic>` to skip the vibe check, produce one lens-tagged list, write no file, and not ask for standouts, so that I can get a fast list with no ceremony.
27. As a user, I want to be able to say "keep this" after a quick run and have it write the doc, so that a good quick list isn't lost.
28. As a user, I want the skill to work on any domain — code, product, writing, naming, business, life — so that I don't need a different tool per subject.
29. As a user, I want the skill not to invoke other skills, so that it stays independent and predictable.
30. As a user, I want a short README beside the skill that says what it is, its stance, and how to tune it, so that a future agent or I can edit it safely.

## Implementation Decisions

**Files.** Three files in `~/.claude/skills/brainstorm/`:
- `SKILL.md` — the runbook. Frontmatter `name` + `description` only; description carries the trigger phrases (`/brainstorm`, "brainstorm"). No `disable-model-invocation` (user-triggered). Body follows suite shape: `# Brainstorm`, orienting line, `##` sections, `## Arguments` table.
- `lenses.md` — one entry per lens: name, one-line prompt the model applies, and whether it's in the default set or held back. Read at the start of every diverge pass.
- `README.md` — ~300 words. Skill map: what it is, stance (sparring partner, user steers), why the doc is light, why it stays independent, how to tune lenses.

**Flow (default mode).**
1. Parse invocation. Detect `quick`. Detect continuation: explicit reference to a prior brainstorm, or slug of topic matches an existing doc in the resolved location.
2. Vibe check: pick ≤3 from the menu {real goal / success shape, hard constraints, already tried or ruled out}, only the ones the invocation didn't answer. Skip if all covered. Do not read local files unless the user says to.
3. Diverge: read `lenses.md`; for each default lens produce 1–3 ideas; total 10–20; numbered, ≤20 words, `[lens]` tag inline. Print list. Stop with one line: "Which grab you? Any thoughts?"
4. Branch on reply: picks → deepen; none/"more"/steer → new round (held-back lenses, or lenses matching the steer, or same lenses aimed at "more like #N"), numbering continues, then stop again.
5. Deepen per standout: one question ("what grabs you about #N?"), then 3–5 riffs and one "would need to be true" line. No ranking, no comparison to prior art. "make concrete" → add effort S/M/L and first step.
6. Write doc; print recap + path.

**Doc location.** `git rev-parse --is-inside-work-tree` succeeds → `./brainstorm-<slug>.md` at cwd. Else `~/brainstorms/<slug>.md` (create dir if missing). Slug: lowercase, hyphenated, ≤5 words from the topic.

**Doc sections.** `# <topic>` / `## Goal & vibe` / `## Ideas` (with `### Round N` subheads from round 2 on) / `## Standouts` / `## Threads` / `## Lens notes`. Goal & vibe records the user's answers in their words plus a `Wildness: balanced` line (fixed for v1). Lens notes is a single line, e.g. `Standouts came from: inversion ×2, borrow ×1.`

**Continuation.** No keyword. On detection, print one line ("Continuing brainstorm-<slug>.md — yes?") and wait. On yes: read doc, dedupe against existing ideas, append round, re-run the stop. Brief change → edit Goal & vibe, add a dated "changed:" line.

**Quick mode.** `quick` as first word after `/brainstorm`. No vibe check, no file, no stop-for-standouts. "keep this" afterwards → write doc from what was generated.

**Repo context.** Off by default. On "look at the repo" / "read X": README, CLAUDE.md, top-level tree, plus named files. Nothing else.

**Voice.** Ideas terse. Riffs terse. The skill's own questions one line each.

**Not in v1.** Sub-agent parallel lenses; wildness dial; auto lens tuning; invoking other skills; a `deep` mode.

## Testing Decisions

No automated tests — this is a prompt artefact. Verification is manual dry runs of these scenarios, judged on external behaviour only (what the user sees, what lands in the doc):

- **T1 fresh, sparse topic** — `/brainstorm names for a running brand` → ≤3 vibe Qs asked, list of 10–20 with all 8 default lenses represented, stop line, no files read.
- **T2 fresh, detailed topic** — invocation states goal, constraints, prior attempts → no vibe Qs, straight to list.
- **T3 zero picks / steer** — reply "more like #4" → new round, numbering continues, ideas cluster near #4, stop again.
- **T4 deepen** — reply "3 and 7" → per standout: one question, then riffs + "would need to be true"; no ranking language.
- **T5 concrete on demand** — "make #3 concrete" → effort + first step added for #3 only.
- **T6 doc write** — inside a git repo → `./brainstorm-<slug>.md` with all five sections; outside → `~/brainstorms/<slug>.md`.
- **T7 continuation** — later `/brainstorm running brand names, fresher` with existing doc → one-line confirm, then round appended, no dupes.
- **T8 quick** — `/brainstorm quick …` → list only, no Qs, no file; "keep this" → doc written.
- **T9 no repo read** — inside a repo with a loud README, topic unrelated → ideas show no README influence; "look at the repo" → they do.

Prior art in this suite: the stop-and-wait beat (print options, stop, wait for the user's pick) and the grouped one-screen terminal report — both already used by existing skills here.

## Out of Scope

- Parallel sub-agents per lens (candidate `deep` mode later).
- A wildness dial or any per-session lens weighting.
- Automatic lens tuning from hit-rate history — the Lens notes line is data for a human, nothing reads it.
- Invoking any other skill from inside brainstorm.
- Any structured store beyond one markdown file per topic.
- The `~/brainstorms` repo's own tooling — it's just a directory under git.

## Further Notes

- The `~/brainstorms/` directory is a separate git repo, private on GitHub (`danielbaldwin47/brainstorms`), created alongside the skill.
- Grill-me and brainstorm are deliberately different shapes: grill-me interrogates to converge, brainstorm generates to diverge. Brainstorm should never drift into relentless questioning.
- The single most likely failure is the deepen phase turning into recommendation. The runbook should say so explicitly.
